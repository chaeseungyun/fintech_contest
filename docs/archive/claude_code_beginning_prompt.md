# Claude Code 착수 프롬프트

아래 전문을 Claude Code 첫 메시지로 붙여넣는다. `scenario.json`과 `화면디자인_v2.html`을 먼저 작업 폴더에 넣어둘 것.

---

## 붙여넣을 내용

핀테크 공모전 데모를 만든다. 발표에서 화면 공유로 시연할 정적 웹 앱이다.

### 무엇을 만드는가

가상 마이데이터 앱의 한 기능이다. 사용자가 급여통장을 다른 은행으로 옮기려 할 때, 그 통장에 걸려 있는 다른 상품들의 우대 혜택이 함께 깨진다는 것을 사전에 보여주고, 언제 옮기면 이번 달 혜택을 지킬 수 있는지 계산한다.

핵심은 두 가지다. 하나의 변경이 **여러 상품에 연쇄**된다는 것, 그리고 조건마다 판정 주기가 달라 **안전한 시점**이 계산으로 나온다는 것.

### 입력 파일

- `scenario.json` — 상품 5건, 조건 5건(UNSUPPORTED 1건 포함), 기대값. 이게 유일한 데이터 소스다.
- `화면디자인_v2.html` — 네 화면의 시안. 레이아웃, 색, 컴포넌트 구조를 여기서 가져온다. 브라우저로 열어서 볼 것.

### 기술 스택

Vite + React + TypeScript. 서버 없음, API 호출 없음, LLM 호출 없음. 정적 빌드 결과물을 그대로 배포한다.
상태는 React state만 사용한다. localStorage를 쓰지 않는다.

### 디렉터리

```
src/
  fixtures/scenario.json
  lib/
    dates.ts          날짜 산술
    interpreter.ts    연산자 평가 → 판정일, 회복 가능 여부
    money.ts          이자·혜택 손실 계산
    graph.ts          binds 역방향 조회
  state/store.ts      단일 상태 객체
  screens/
    Connections.tsx   화면 1 관계도
    Impact.tsx        화면 2 변경 영향
    Timing.tsx        화면 3 시점
    Evidence.tsx      화면 4 근거
  components/         SourceTag, PhoneFrame 등
```

### 계산 규칙 — 여기가 이 프로젝트의 본체다

**날짜 (`dates.ts`)**
- 타임존 `Asia/Seoul` 고정. 시각 없이 날짜만 다룬다. `Date` 객체의 시분초를 절대 쓰지 않는다.
- 구간은 반열림 `[start, end)`로 통일한다.
- 월 오프셋은 말일 clamping을 한다. 1/31에 `+1M`은 2/28(29)이다.
- 년·월·일 오프셋이 섞이면 년 → 월 → 일 순서로 적용한다. 순서를 바꾸면 결과가 달라진다.
- 오늘은 `scenario.json`의 `meta.today`를 쓴다. **`new Date()`를 호출하지 않는다.** 발표 당일 타임라인이 깨진다.

**연산자 평가 (`interpreter.ts`)**

각 조건의 `expr.op`에 따라 "다음 판정일"과 "회복 가능 여부"를 낸다.

- `RECUR` — `params.from.dayOfMonth` 기준으로 오늘 이후 첫 판정일. 오늘이 그 날이면 오늘로 본다.
- `ROLLING` — `params.settleOn`이 `month_end`면 이번 달 말일.
- `COUNT` — `params.checkOn.dayOfMonth` 기준 다음 확인일.
- `PERMANENT` — 판정일 없음(`null`). 회복 불가로 표시하고 `params.until` 앵커를 상품의 `facts.maturity`로 바인딩해 회복 시점을 낸다.

전체 안전 시점은 회복 가능한 조건들의 판정일 중 **가장 늦은 날**이다. 그 날이 지나면 이번 달 판정이 모두 끝난 상태가 된다.

**금액 (`money.ts`)**
- `effect.kind === "rate_delta"` — 원금 × |금리차| = 연간 손실. 대출은 첫해 기준이므로 그렇게 라벨링한다.
- `effect.kind === "monthly_benefit"` — 월 금액 × 12.
- 모든 금액은 연 단위로 통일한다. 상품마다 만기가 달라 총액으로는 더할 수 없다.
- 순수 함수로 작성한다. 같은 입력에 항상 같은 값이 나와야 한다.

**연쇄 (`graph.ts`)**
- `binds.target`이 변경 대상 상품을 가리키는 조건을 전부 찾는다.
- 각 조건의 `binds.holder`가 영향받는 상품이다.
- 관계도의 선은 이 배열을 순회해 그린다. **SVG를 손으로 박아두지 않는다.** 조건이 늘면 선도 늘어야 한다.

### 화면

시안 HTML의 네 화면을 그대로 구현한다. 폰 프레임은 CSS로 그리고, 데스크톱에서는 네 화면을 나란히 볼 수 있게 한다.

1. **내 금융 연결** — 급여통장을 중심에 둔 관계도. 위성 노드는 조건 배열에서 생성. 선을 누르면 해당 약관 원문이 뜬다.
2. **변경 영향** — 합계 손실 하나만 크게. 아래 상품별 내역을 금액 큰 순으로. 결론 배너는 회복 가능 건과 회복 불가 건을 나눠 쓴다.
3. **시점** — 오늘부터의 축에 안전 구간을 색으로 칠하고, 조건별 판정일을 목록으로. PERMANENT 조건은 다른 색으로 구분하고 별도 박스에서 만기까지 회복 불가임을 설명한다.
4. **근거** — 약관 원문에 `spans`로 하이라이트. 아래에 추출된 값 목록. `감면 폭`, `판정 주기`, `실적 기준` 세 개는 실제로 수정 가능해야 한다.

### 출처 태그 — 반드시 지킬 것

화면에 뜨는 모든 수치에 네 종류 중 하나의 태그가 붙는다.

| 태그 | 색 | 무엇 |
|---|---|---|
| 약관에서 추출 | `#5B4BB8` / 배경 `#EDE9FB` | 조건의 `expr`, `binds`, `effect` |
| 계산 결과 | `#0F766E` / 배경 `#DCF2EF` | 판정일, 손실 금액, 안전 시점 |
| 보유 상품 정보 | `#6B7280` / 배경 `#EDEFF2` | `products[].facts` |
| 사용자 확인 | `#B45309` / 배경 `#FBEEDC` | 사용자가 수정한 값 |

태그는 **값과 같은 객체에 담는다.** 화면에서 조건문으로 붙이지 않는다. 값을 만드는 함수가 출처를 함께 반환하는 구조로 만든다.

### 절대 하지 말 것

- 금액이나 날짜를 문자열로 하드코딩하지 않는다. `800,000`이나 `2026-09-30`을 JSX에 직접 쓰면 수정 기능이 무의미해진다. `scenario.json`의 `expected` 블록은 테스트용이지 표시용이 아니다.
- `new Date()`를 호출하지 않는다.
- localStorage, sessionStorage를 쓰지 않는다.
- 네 화면이 각자 값을 복사해 갖지 않는다. 단일 상태 객체를 공유한다.

### 만드는 순서

1. `dates.ts`와 테스트. 말일 clamping, 오프셋 순서, 다음 판정일 세 가지를 검증한다.
2. `interpreter.ts`와 `money.ts`. `scenario.json`의 `expected` 블록을 그대로 테스트 케이스로 쓴다. 여기까지 통과하면 나머지는 표시 작업이다.
3. `graph.ts`.
4. 화면 2 → 3 → 4 → 1 순서로 만든다. 관계도가 가장 손이 많이 가고 계산과 무관하므로 마지막이다.
5. 화면 4의 수정 → 재계산 연결. **이게 시연의 핵심 장면이다.** 실적 기준을 30만원에서 60만원으로 바꾸면 화면 2의 합계와 화면 3의 날짜가 즉시 바뀌어야 한다.
6. 데모 초기화 버튼. 발표 중 두 번 시연할 수 있어야 한다.

### 완료 기준

- `expected` 블록의 모든 값이 코드 계산으로 재현된다.
- 화면 4에서 값을 고치면 화면 2·3이 따라 바뀐다.
- 같은 조작을 두 번 하면 같은 숫자가 나온다.
- 조건을 하나 지우면 관계도의 선도 하나 줄어든다.

먼저 1번(`dates.ts`)만 만들고 테스트 결과를 보여달라. 날짜 계산이 틀리면 그 위의 전부가 틀린다.

## 프롬프트에 일부러 넣은 것

- **마지막 문장** — 한 번에 전부 만들게 하면 날짜 계산의 오류가 화면까지 묻혀 들어간다. 첫 응답을 `dates.ts`로 끊어서 기초를 먼저 본다.
- **`expected` 블록을 테스트 케이스로 지정** — 기대값을 미리 주면 구현이 거기에 맞춰지고, 틀렸을 때 어디가 틀렸는지 즉시 드러난다.
- **하드코딩 금지를 명시** — 안 적어두면 화면부터 만들면서 숫자를 박아넣는다. 그러면 수정 기능이 죽는다.
- **화면 1을 마지막에 배치** — 관계도가 가장 눈에 띄는 화면이라 먼저 만들고 싶어지는데, 계산과 무관해서 먼저 만들면 시간만 쓴다.
